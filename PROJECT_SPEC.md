# Техническое задание MiningGame

MiningGame — учебный проект на Go об управлении угольной шахтой. Его цель — закрепить работу с интерфейсами, конкурентностью, HTTP и REST API. При выполнении задания важнее наглядно применить изученные механизмы, чем построить идеальную production-архитектуру.

## Цель игры

Игрок управляет предприятием «Угольная шахта». Для победы необходимо купить всё обязательное оборудование за минимально возможное время.

Уголь одновременно является добываемым ресурсом и внутренней валютой. Им оплачивается найм шахтёров и покупка оборудования, а весь добытый уголь поступает на общий баланс предприятия.

## Доход предприятия

- С момента запуска предприятие получает пассивный доход: `1` единица угля в секунду.
- Пассивный доход создаёт отдельная фоновая горутина, которая раз в секунду отправляет одну единицу угля в общий поток прибыли.
- Игрок расходует накопленный баланс на найм шахтёров и покупку оборудования.
- Покупка всего оборудования только за счёт пассивного дохода допустима, но противоречит цели закончить игру за минимальное время.

## Классы шахтёров

Набор классов является закрытым и состоит ровно из трёх значений. Классы нельзя создавать, изменять или удалять через API.

| Класс | Стоимость найма | Количество добыч | Начальная добыча за цикл | Интервал | Прогрессия |
| --- | ---: | ---: | ---: | ---: | --- |
| Маленький | 5 угля | 30 | 1 уголь | 3 секунды | Нет |
| Нормальный | 50 угля | 45 | 3 угля | 2 секунды | Нет |
| Сильный | 450 угля | 60 | 10 угля | 1 секунда | После каждой добычи объём следующей добычи увеличивается на 3 |

Игрок сам решает, шахтёра какого класса и в какой момент нанять.

При найме HTTP-клиент выбирает только идентификатор одного из допустимых классов. Стоимость, запас добыч, объём добычи, интервал и прогрессия определяются сервером и не принимаются от клиента. Неизвестный идентификатор класса должен отклоняться. Для сильного шахтёра последовательность объёма добычи начинается как `10`, `13`, `16` и далее увеличивается на `3` после каждого цикла.

## Работа шахтёров

- Каждый нанятый шахтёр работает в отдельной горутине.
- Через заданный для его класса интервал шахтёр добывает уголь и передаёт его в общий поток прибыли предприятия.
- Каждая добыча расходует одну единицу запаса энергии, выраженного количеством оставшихся добыч.
- Когда запас добыч исчерпан, горутина шахтёра завершается.
- Все шахтёры зависят от контекста предприятия.
- Предприятие может в любой момент отменить общий контекст и немедленно инициировать завершение всех шахтёров, не ожидая следующего цикла добычи.

Шахтёры хранятся на предприятии через интерфейс, чтобы добавление новых реализаций не требовало менять внутреннюю логику предприятия:

```go
// Coal — уголь.
// MinerInfo — информация о шахтёре: класс, оставшаяся энергия и другие параметры.
type Miner interface {
	Run(ctx context.Context) <-chan Coal
	Info() MinerInfo
}
```

Для завершения игры необходимо приобрести всё перечисленное оборудование:

| Оборудование | Стоимость |
| --- | ---: |
| Кирки | 3 000 угля |
| Вентиляция в шахту | 15 000 угля |
| Вагонетки | 50 000 угля |

## Состояние предприятия

Предприятие хранит:

- текущий баланс угля;
- список работающих в данный момент шахтёров;
- класс и оставшуюся энергию каждого работающего шахтёра;
- общее количество нанятых шахтёров каждого класса за всё время игры, включая уже завершивших работу;
- состояние каждого вида оборудования: приобретено оно или нет;
- время запуска и данные, необходимые для расчёта полной продолжительности игры.

Общий баланс и остальное изменяемое состояние предприятия должны быть защищены от гонок данных. Проверка достаточности баланса и списание стоимости найма или покупки выполняются как одна атомарная операция относительно других изменений баланса.

## Завершение игры

Команду на завершение отправляет игрок после покупки всего обязательного оборудования.

При успешном завершении предприятие должно:

1. Проверить, что всё обязательное оборудование приобретено.
2. Вернуть накопленную статистику, включая время достижения цели.
3. Отменить контекст и завершить всех работающих шахтёров.
4. Остановить фоновый пассивный доход.
5. Корректно завершить HTTP-сервер.
6. Завершить игру.

## Возможности HTTP API

Взаимодействие игрока с игрой осуществляется по HTTP. Контракт по возможности проектируется в стиле REST.

### Шахтёры

API должно позволять:

- получить характеристики и стоимость найма каждого из трёх классов;
- нанять шахтёра выбранного класса;
- получить список всех работающих шахтёров;
- отфильтровать работающих шахтёров по классу.

Для текущего контракта зафиксированы следующие решения:

- `GET /miners/types` — получить закрытый каталог из трёх классов и их характеристик;
- `GET /miners` — получить всех работающих шахтёров;
- `GET /miners?type=<class>` — получить работающих шахтёров выбранного класса;
- `POST /miners` — нанять шахтёра выбранного класса.

`/miners/types` является только доступным для чтения справочником. Это не CRUD-ресурс, потому что состав классов задан правилами игры.

### Оборудование

API должно позволять:

- получить стоимость всех видов оборудования;
- купить выбранное оборудование;
- получить информацию о приобретённом и ещё не приобретённом оборудовании.

Конкретные URL и форматы запросов для оборудования определяются при проектировании HTTP-контракта.

### Предприятие

API должно позволять:

- получить промежуточное состояние предприятия, включая текущий баланс и статистику найма;
- отправить команду на завершение игры.

Состав дополнительной промежуточной статистики и конкретные URL определяются при проектировании HTTP-контракта.
